# Домашнее задание к занятию «Базы данных, их типы» - Абанина Максима

## Задание 1 - СУБД
Кейс
Крупная строительная компания, которая также занимается проектированием и девелопментом, решила создать правильную архитектуру для работы с данными. Ниже представлены задачи, которые необходимо решить для каждой предметной области.

Какие типы СУБД, на ваш взгляд, лучше всего подойдут для решения этих задач и почему?

1.1. Бюджетирование проектов с дальнейшим формированием финансовых аналитических отчётов и прогнозирования рисков. СУБД должна гарантировать целостность и чёткую структуру данных.
Ответ: Рекомендуемый тип: Реляционная СУБД (OLTP + OLAP)
Конкретные примеры: PostgreSQL, Oracle Database, MS SQL Server

1.1.* Хеширование стало занимать длительно время, какое API можно использовать для ускорения работы?
Ответ: технологии API - Intel IPP (Integrated Performance Primitives), Intel SHA Extensions (SHA-NI), CUDA API (NVIDIA) - на мой взгляд самый лучший вариант ибо графический процессор в разы быстрее, не зря его мощности используют в хакерских атаках, OpenSSL EVP API, xxHash / CityHash / FarmHash (через C-библиотеки).

1.2. Под каждый девелоперский проект создаётся отдельный лендинг, и все данные по лидам стекаются в CRM к маркетологам и менеджерам по продажам. Какой тип СУБД лучше использовать для лендингов и для CRM? СУБД должны быть гибкими и быстрыми.
Ответ: Рекомендуемый тип: Документоориентированная NoSQL СУБД
Конкретные примеры: MongoDB, Couchbase

1.2.* Можно ли эту задачу закрыть одной СУБД? И если да, то какой именно СУБД и какой реализацией?
Ответ: По моему мнению, возможно. Лучший кандидат — PostgreSQL с JSONB.

1.3. Отдел контроля качества решил создать базу по корпоративным нормам и правилам, обучающему материалу и так далее, сформированную согласно структуре компании. СУБД должна иметь простую и понятную структуру.
Ответ: Рекомендуемый тип: Документоориентированная СУБД с поддержкой иерархий
Конкретные примеры: MongoDB, Elasticsearch (как хранилище + поисковый движок)

1.3.* Можно ли под эту задачу использовать уже существующую СУБД из задач выше и если да, то как лучше это реализовать?
Ответ: Возможно, если выбрано PostgreSQL.

1.4. Департамент логистики нуждается в решении задач по быстрому формированию маршрутов доставки материалов по объектам и распределению курьеров по маршрутам с доставкой документов. СУБД должна уметь быстро работать со связями.
Ответ: Рекомендуемый тип: Графовая СУБД
Конкретные примеры: Neo4j, Amazon Neptune, ArangoDB (графовый режим) - больше визуала в СУБД.

1.4.* Можно ли к этой СУБД подключить отдел закупок или для них лучше сформировать свою СУБД в связке с СУБД логистов?
Ответ: лучше сделать отдельную реляционную СУБД для закупок + интеграция с графовой СУБД логистов, так как разные задачи и наполнение СУБД

1.5.* Можно ли все перечисленные выше задачи решить, используя одну СУБД? Если да, то какую именно?
Ответ: Теоретически — да. Практически — с оговорками. Лучший кандидат - PostgreSQL.

## Задание 2 - Транзакции
2.1. Пользователь пополняет баланс счёта телефона, распишите пошагово, какие действия должны произойти для того, чтобы транзакция завершилась успешно. Ориентируйтесь на шесть действий.
Ответ:
Шаг 1. Инициация и валидация входных данных
Пользователь нажимает кнопку «Пополнить». Система проверяет корректность данных: авторизован ли пользователь, корректен ли номер телефона, попадает ли сумма в допустимые лимиты.
Результат: Данные валидны, система готова к созданию платежа.
Шаг 2. Открытие транзакции и создание «черновика» (резервирование)
Система открывает транзакцию в БД, создается запись в таблице payments со статусом PROCESSING (или PENDING), генерируется уникальный idempotency_key (ключ идемпотентности), чтобы при случайном дубле запроса от фронта или сети банк не списал деньги дважды.
Шаг 3. Взаимодействие с платежным шлюзом (банком)
Система отправляет API-запрос в банк или платежный шлюз (эквайринг) с данными карты и суммой, банк проверяет наличие средств, лимиты, антифрод-системы, если всё хорошо, банк резервирует/списывает средства и возвращает системе статус SUCCESS (или присылает асинхронный webhook).
Шаг 4. Обновление бизнес-сущностей в БД
Получив успешный ответ от банка, система открывает новую транзакцию БД для фиксации результата, блокирует строку с балансом пользователя (например, через SELECT ... FOR UPDATE, чтобы избежать состояния гонки при одновременных запросах), увеличивает баланс телефона на сумму пополнения (balance = balance + amount), обновляет статус платежа в таблице payments с PROCESSING на SUCCESS.
Шаг 5. Фиксация транзакции (COMMIT)
Система отправляет команду COMMIT, все изменения (новый баланс и статус платежа) становятся перманентными и видимыми для других сессий, блокировки со строки баланса снимаются.
Шаг 6. Асинхронная финализация и уведомления
После успешного коммита система инициирует фоновые задачи (обычно через очередь, например, RabbitMQ/Kafka) - отправка SMS/Push-уведомления пользователю об успешном пополнении, отправка электронного чека на почту, запись данных в аналитику и синхронизация с бухгалтерской системой.

2.1.* Какие действия должны произойти, если пополнение счёта телефона происходило бы через автоплатёж?
Ответ:
Главное отличие автоплатежа — это переход от синхронного сценария (где пользователь ждёт результата здесь и сейчас) к асинхронному сценарию с развитой машиной состояний (Status Machine), где система должна уметь корректно обрабатывать отложенные отказы, повторять попытки и управлять жизненным циклом токена.

## Задание 3 - SQL vs NoSQL
3.1. Напишите пять преимуществ SQL-систем по отношению к NoSQL.
Ответ: 
1. Гарантированная целостность данных (ACID)
2. Строгая схема и валидация на уровне СУБД
3. Мощные JOIN-операции и аналитические возможности
4. Зрелость экосистемы и стандартизация
5. Зрелые механизмы репликации, бэкапов и отказоустойчивости
   
3.1.* Какие, на ваш взгляд, преимущества у NewSQL систем перед SQL и NoSQL.
Ответ:
NewSQL — это современное поколение СУБД, которое пытается объединить лучшее от обоих миров:
От SQL: реляционная модель, SQL-интерфейс, ACID-транзакции
От NoSQL: горизонтальная масштабируемость, распределённость, высокая доступность
Яркие представители: CockroachDB, TiDB, Google Spanner, YugabyteDB, VoltDB, MemSQL (SingleStore).
Ключевые преимущества NewSQL: Горизонтальная масштабируемость + ACID (главное преимущество), автоматическое шардирование и ребалансировка, глобальная репликация и низкая задержка, единый SQL-интерфейс без компромиссов, еlasticity — масштабирование на лету, 
NewSQL — это эволюция SQL-систем для эпохи облаков и глобальных приложений. Они закрывают главный разрыв между SQL (целостность, но плохая масштабируемость) и NoSQL (масштабируемость, но слабая целостность), предлагая «лучшее из обоих миров» за счёт распределённых консенсус-алгоритмов и автоматического шардирования.

## Задание 4 - Кластеры
Необходимо производить большое количество вычислений при работе с огромным количеством данных, под эту задачу выделено 1000 машин.
На основе какого критерия будете выбирать тип СУБД и какая модель распределённых вычислений здесь справится лучше всего и почему?
Ответ:
Главным критерием выбора типа СУБД в данном случае является характер рабочей нагрузки (паттерн доступа к данным) и модель хранения.
Если коротко: нам нужна OLAP-система (Online Analytical Processing) с колоночным хранением данных, а не OLTP (система для транзакций).
Резюме - Для кластера из 1000 машин с огромным объемом данных оптимальная архитектура будет гибридной (Data Lakehouse / Lakehouse):
Хранилище (СУБД): Колоночная OLAP-СУБД (например, ClickHouse или Greenplum), работающая по модели MPP (Shared-Nothing). Она возьмет на себя тяжелые SQL-агрегации, фильтрации и выдачу бизнес-аналитики с минимальной задержкой. Вычислительный движок (для сложных задач): Распределенный фреймворк Apache Spark (или Apache Flink), использующий модель In-Memory DAG. Он будет использоваться для сложной математической обработки, машинного обучения и подготовки данных, читая данные напрямую из распределенного хранилища (например, из S3/HDFS или напрямую из таблиц OLAP-СУБД). 
Такой симбиоз закроет 100% потребностей в вычислениях, обеспечив и высокую скорость SQL-запросов (за счет MPP), и гибкость для нестандартных алгоритмов (за счет In-Memory DAG).
